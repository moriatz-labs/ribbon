Technical architecture

One product workflow. Swappable providers.

The basic stack is Hostinger, Supabase, and Vercel. Capability adapters also support Cloudflare, Firebase, and Netlify without changing the product UI.

Runtime plane

Each capability has one selected adapter

The manifest selects DNS, deployment, backend, and mail providers. The application UI talks only to stable capability contracts.

UserBrowser and provider-neutral session
DNS adapterOptional: Hostinger or Cloudflare
DeploymentVercel, Netlify, or Firebase Hosting
BackendSupabase or Firebase Auth + Firestore
Control plane

Codex + Ribbon CLI

Scaffolds, checks, inventories, links, and records URLs without logging secret values.

Build input

Strawn from npm

Exact package versions provide shared primitives, providers, and icons to every app.

Release authority

GitHub Actions

Security defaults

  • Only publishable provider configuration in the browser
  • Supabase RLS or owner-scoped Firebase rules
  • Private storage with user-prefixed object paths
  • DNS and deployment tokens stay outside application code

Release defaults

  • Standalone Vite projects
  • Frozen pnpm lockfiles and cached downloads
  • One verified artifact per deployment
  • Provider-matched GitHub Actions workflow

Provisioning rule: Hostinger and Cloudflare use the same conflict-safe CNAME contract. The target comes from the selected Vercel or Netlify adapter, and Cloudflare routes remain DNS-only.
